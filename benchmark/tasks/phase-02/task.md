# Phase 02 — 批量导入与匹配执行

## 目标

在已通过人工验收的 Phase 01 单曲闭环上，实现可实际使用的批量导入流程：导入多个音频、LRC 和封面资源，生成确定性匹配预览，允许用户处理冲突和未匹配资源，确认不可变执行计划，以有界并发逐项处理，持久化进度，并下载批量 ZIP 与 JSON 报告。

本轮只有 Codex 继续开发。Claude 已淘汰，不得读取、比较、引用或复制 Claude 的目录、分支、提交、报告、会话和实现。

## 必须完成

### 1. 批量导入页面

- 首页清楚区分“单曲编辑”和“批量导入”。
- 支持多选文件以及浏览器目录选择；尽可能保留安全的相对目录信息。
- 接受 MP3、FLAC、WAV、LRC、JPEG 和 PNG；其他格式进入不支持列表，不得静默忽略。
- 上传后显示总数、音频数、歌词数、封面数、不支持数、待确认数和冲突数。
- 页面必须为中文响应式界面，不依赖外部 CDN。
- 刷新页面后，可以通过任务 ID 从 MySQL 恢复待确认状态和处理进度。

### 2. 确定性匹配与人工确认

- 首选规则：同一相对目录内，忽略扩展名后的完整文件名唯一一致。
- 次选规则：音频标签与 LRC 的 `[ti:]`、`[ar:]` 明确且唯一一致。
- 只有唯一且强确定性的候选可以自动匹配。
- 同名不同目录、同名多个候选、标签冲突和重复绑定必须进入冲突列表，禁止猜测。
- 清楚分类：完全匹配、部分匹配、冲突/待确认、未匹配资源、不支持/损坏。
- 每首音频展示当前标签、候选歌词、候选封面、匹配依据、警告和执行/跳过选择。
- 允许用户手动指定或取消歌词、封面绑定；未匹配资源单独展示。
- 用户确认后保存不可变 `ProcessingPlan` 快照；后台执行不得重新匹配或悄悄改变计划。

### 3. 批量执行

- 使用可配置的有界并发，默认并发数应保守，禁止无界线程和一次性把所有大文件读入内存。
- 每首歌独立处理；单项失败不能回滚或阻断其他歌曲。
- 复用 Phase 01 的原件保护、工作副本、写后重读、新版本、父版本、下载和报告能力，不得另写一套冲突实现。
- 持久化批任务和每个任务项的状态、当前阶段、错误码、用户提示、诊断标识和输出版本。
- 提供整体进度及成功、失败、跳过、等待数量。
- 支持只重试失败项；已经成功的项目不得重复生成版本。
- 应用重启后不得把仍在执行的项目虚假标记为成功；提供明确的中断/可重试状态。

### 4. ZIP 与报告

- 批任务完成后可下载 ZIP，包含成功成品及机器可读 JSON 报告。
- ZIP 内文件名必须安全、稳定并处理重名；不得包含绝对路径、`..`、Secret、临时文件或失败工作副本。
- 部分成功时仍允许下载成功项，报告必须列出每个项目的状态、阶段、错误码和修复提示。
- JSON 报告必须能依据 MySQL 中的任务事实重新生成。

### 5. 数据库演进

- MySQL 是正式运行时唯一事实来源；内存实现只能作为明确的单元测试替身。
- 使用新的 Flyway 版本迁移，例如 `V2__phase02_batch_import.sql`；不得修改已经发布的 V1 校验内容。
- 不删除数据库，不要求用户重建数据库，不在人工 SQL 中创建业务表。
- 新迁移必须能在已有 Phase 01 数据的数据库上直接升级，并保留全部历史记录。
- Repository 接口必须隔离业务用例与 JDBC 细节。
- 地址和凭据仅从本地忽略配置或环境变量读取。

### 6. 文件与安全边界

- 服务端存储名由 ID 生成；原始文件名和相对路径只用于显示与匹配。
- 拒绝绝对路径、目录穿越、符号链接逃逸、空文件、伪造扩展名和超限文件。
- 限制单文件、单批文件数和单批总大小，全部可配置并在页面显示。
- 不提交真实地址、主机名、账号、密码、Token、连接串、SSH 材料、个人部署路径、媒体、运行数据或构建产物。
- `src/test/` 必须提交；测试生成物只能进入 Git 忽略目录或仓库外目录。

### 7. 自动验证

至少覆盖：

- 精确文件名匹配、LRC 标签匹配、部分匹配。
- 同名不同目录、多候选冲突、重复绑定和未匹配资源。
- 人工改绑后计划快照保持不变。
- MP3 与 FLAC 混合批次的部分成功。
- 单项失败不阻断其他项。
- 失败项重试且成功项不重复执行。
- 刷新/重启后的任务和进度恢复。
- ZIP 重名、安全路径及 JSON 报告一致性。
- 危险相对路径、空文件、伪造格式、文件数和总大小限制。
- V2 在已有 V1 schema 和数据上的升级。

必须实际运行 Java 17 下的：

```text
mvn clean verify
mvn package
git diff --check
```

使用仓库外原创样本生成一组可人工检查的批量验收产物，至少包含成功 MP3、成功 FLAC、一个明确失败项、批量 ZIP 和 JSON 报告。产物不得自动删除。

真实 M710q MySQL 集成验证应使用用户已有的本地私密配置。若工具权限阻止连接，不得因此停止其余实现；如实标记 `PENDING USER EXECUTION`，不得用 H2 结果冒充 MySQL 证据。

## 人工验收

1. 选择含 MP3、FLAC、LRC、封面、同名冲突和无关文件的目录。
2. 检查自动匹配依据、部分匹配、冲突和未匹配分类。
3. 手工改绑一个冲突项，跳过一个项目并确认计划。
4. 开始执行，观察进度；确认一个失败项不影响其他成功项。
5. 刷新页面，确认任务和进度仍可恢复。
6. 只重试失败项，确认成功项没有重复版本。
7. 下载 ZIP 和 JSON，检查音乐可播放、标签正确、文件名安全、报告与数据库一致。
8. 重启应用，再次查看任务和下载结果。
